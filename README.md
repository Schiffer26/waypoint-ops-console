# WAYPOINT — Personal Operations Console

An industrial-styled Windows 10/11 desktop productivity console — tasks, schedule, calendar
and a reliable background reminder engine. Fully offline: all data stays on your machine,
with no cloud service and no account.

**Stage 03** moves reminder scheduling entirely into the Electron main process, so
notifications fire whether the dashboard is open, minimised, hidden in the tray, or never
opened at all — plus multiple reminders per entry, snooze, missed-reminder catch-up, a
delivery ledger with notification history, and selectable notification sounds. It builds on
Stage 01 (console + calendar), Stage 02A (adaptive theming, Daily Briefing, tray,
launch-at-login) and Stage 02A.1 (integration fixes).

Visual identity: minimalist industrial science-fiction — paper surfaces, charcoal chrome,
acid yellow accents, mint status signals, Space Grotesk display type, JetBrains Mono technical
labels, chamfered geometry and corner brackets. Motion is deliberate and reduced-motion aware.

> ⚠️ **Read this first.** WAYPOINT was developed and tested in a **Linux cloud sandbox with
> no Windows machine**. All logic, builds and automated suites pass there, and
> electron-builder successfully packaged `WAYPOINT.exe` — but Windows-only behaviour
> (toast rendering and buttons, tray, login item, sound, sleep/resume, the NSIS installer)
> has **not** been verified on real Windows hardware. See
> [Verification status](#verification-status--what-is-proven-and-where) and the
> [Windows verification checklist](#windows-verification-checklist) before relying on it.

## Run it on your Windows PC

WAYPOINT was developed in a Linux cloud sandbox. Everything below is what you need to get
it running — and to produce a real installer — on your own Windows machine.

### Prerequisites (Windows 10 / 11)

| Requirement | Notes |
| ----------- | ----- |
| **Node.js 20 LTS or newer** | <https://nodejs.org> — includes npm. Verify with `node -v`. |
| **Git** *(optional)* | Only if you clone rather than copy the exported folder. |
| ~1.5 GB free disk | Electron binary + build output. |

No Python, no image libraries and no native build tools are required: the icon and
notification sound are generated by dependency-free Node scripts.

### 1 — Export and install

Copy/clone the project folder to your PC, then from a terminal **in the project root**:

```powershell
npm install            # installs deps and downloads the Electron binary
```

> If you copied the folder from the sandbox, delete any existing `node_modules` and
> `release` folders first — they are platform-specific.

### 2 — Run it in development

```powershell
npm run desktop:dev    # generates assets, compiles main+preload, starts Vite, opens Electron
```

This is the fastest way to exercise the real desktop app (tray, briefing, notifications)
with hot-reloading UI. `npm run dev` alone opens only the browser preview, which has no
Electron main process and therefore no background scheduler.

### 3 — Build the Windows installer

```powershell
npm run desktop:pack   # → release\WAYPOINT-Setup-0.3.0.exe  (+ release\win-unpacked\)
```

This runs the renderer build, generates `assets/`, compiles the Electron main process and
invokes electron-builder's NSIS target. Then install it:

```powershell
.\release\WAYPOINT-Setup-0.3.0.exe
```

Choose a per-user install (the default) so no admin rights are needed.

> **Install the built app before judging notifications.** Windows only shows toasts for an
> application that has a Start Menu shortcut whose AppUserModelID matches the one the app
> registers (`com.waypoint.console`). The NSIS installer creates that shortcut; running
> `electron .` directly from source does not, so toasts may be silently suppressed in
> dev mode. See *Windows verification checklist* below.

### Troubleshooting

| Symptom | Fix |
| ------- | --- |
| No toasts appear | Install via the NSIS installer (not `electron .`); check Settings › Notifications are on and Windows **Focus assist / Do not disturb** is off; confirm WAYPOINT is allowed in *Windows Settings → System → Notifications*. |
| Tray icon missing | Windows hides new tray icons by default — open the tray overflow (**^**) and drag WAYPOINT onto the taskbar. |
| `npm run desktop:pack` fails on a non-Windows host | Building the NSIS installer from Linux/macOS needs `wine`. Build on Windows (or install wine) — see *Known environment limits*. |
| Reminders never fire | WAYPOINT must stay running (tray counts). Anything missed while it was closed is replayed on next launch within the 24h catch-up window. |

## Stage 02A features

### Adaptive appearance (Settings › 00 Appearance)

| Option           | Behaviour                                                              |
| ---------------- | ---------------------------------------------------------------------- |
| SYSTEM DEFAULT   | Follows Windows light/dark live (`prefers-color-scheme`). **Default.** |
| LIGHT MODE       | Forces the approved Stage-01 paper appearance.                         |
| DARK MODE        | `#111111` grid background, `#202020/#292929` surfaces, `#383838` lines, `#F2F2EE` keylines, acid/mint accents retained. |

The preference persists in the store (`settings.theme`) and applies on `<html data-theme>`,
driving the scoped semantic token layer — chrome surfaces (sidebar, countdown panels, toasts,
briefing) stay constant so contrast relationships never invert.

### Daily Briefing (Windows startup)

Launching with `--waypoint-startup` shows a compact frameless popup instead of the console:

- WAYPOINT identity + version, live clock, personalized greeting (saved operator name)
- today/overdue/cleared counters, today's event schedule, next transmission + live countdown
- operational status line (`ALL SYSTEMS NOMINAL` / `ATTENTION REQUIRED`)
- **OPEN MAIN CONSOLE** → restores the dashboard · **DISMISS** → closes only the popup

Rules implemented in `electron/main.ts`:

| Rule | Behaviour                                                                             |
| ---- | ------------------------------------------------------------------------------------- |
| A    | Login launch → tray-dormant; briefing opens when `settings.briefingAtLogin` is on      |
| B    | Manual launch → full dashboard, no briefing                                            |
| C    | Briefing dismiss / console close → window hides; app keeps running via the tray        |
| D    | Tray **Quit WAYPOINT** → `isQuitting` flag, normal process termination                 |

Two independent persisted settings: **Launch at login** (OS login item, registered *and*
read with the matching `--waypoint-startup` arg) and **Daily Briefing at login** (stored in
the app settings, read by the main process from the persisted store file before opening the
popup). Settings › System Integration exposes both plus a PREVIEW BRIEFING action.

### System tray

Branded chamfered acid-W icon (`assets/tray-icon.png`, also used for the app icon via
`build/icon.png`). Menu: **Show WAYPOINT · Open Daily Briefing · Add Task · Quit WAYPOINT**.
Tray-click restores the console. Add Task focuses the console and opens the entry editor via
a preload-bridged push channel (`onOpenCreate`). Single-instance guard hands focus to the
running instance on relaunch.

## Data safety & migration

Persistence is at **v4**. Migrations run in order and are strictly additive — existing
tasks, events, categories, completed records and preferences are preserved verbatim; only
new fields are introduced.

| Step | Adds | Existing data |
| ---- | ---- | ------------- |
| v1 → v2 | appearance + Daily Briefing settings | untouched |
| v2 → v3 | multi-offset reminders (`offsets[]`), reminder-engine settings | legacy `{enabled, minutesBefore}` folded into `offsets[]`; `minutesBefore` still written so older builds and previously exported JSON keep working |
| v3 → v4 | monthly recurrence anchor (`repeatAnchorDay?`) | stamped from each monthly entry's own `date`; non-monthly entries untouched; absent values are derived at read time |

Every new field is **optional**, so a database from any earlier stage loads without
rewriting or discarding records. Verified by the smoke suite (`v1 venue` checks) and the
recurrence suite (legacy entries with no stored anchor).

## Stage 03 — autonomous background reminder engine

Reminder scheduling now lives **entirely in the Electron main process**. The old
`src/App.tsx` interval is gone from the desktop path (it remains only as a web-preview
fallback, which has no main process) — so reminders fire while the dashboard is minimised,
hidden in the tray, never opened, or while the operator works in another app.

> The app must be running (tray counts) for live delivery. Anything that elapses while
> WAYPOINT or Windows is off is recovered by missed-reminder catch-up on the next launch.

### Architecture

| Module | Role |
| ------ | ---- |
| `electron/recurrence.ts` | **Shared + pure** recurrence maths (anchored monthly, daily, weekly). Imported by the scheduler **and** the renderer calendar, so occurrence dates can never diverge. |
| `electron/reminder-core.ts` | **Pure** engine: occurrence expansion, reminder identity, the single `planReminders()` decision function, ledger state machine. No Electron/Node imports → fully unit-testable with a fake clock. |
| `electron/scheduler.ts` | Electron shell: 15s tick, `powerMonitor` resume/unlock rescans, native notifications, Windows toast XML, sound, snooze API. |
| `electron/ledger-store.ts` | Atomic (`tmp` → `fsync` → `rename`) persistence of `waypoint-reminder-ledger.json`. |
| `electron/db-reader.ts` | Read-only decode of the renderer-owned `waypoint-store.json`. The main process **never writes** it. |

Scheduling is **recalculated**, not pre-armed: there is no `setTimeout` per entry. A single
interval plus event-driven rescans (renderer write, power resume, snooze) keeps thousands of
reminders free. A rescan is triggered inside the `storage:write` IPC handler, so the order
"renderer persists → engine recalculates" is guaranteed.

### Multiple reminders per entry

Offsets: **at time · 5 min · 15 min · 30 min · 1 hour · 1 day** — any combination per entry.
An event on 10 Nov at 14:00 with all four of the spec's offsets produces reminders at
09 Nov 14:00, 10 Nov 13:00, 13:45 and 14:00 (asserted in the test suite).

**Migration (v2 → v3)** folds the legacy `{ enabled, minutesBefore }` into `offsets[]` for
every task and event; `minutesBefore` is still written so previously exported JSON — and
older builds — keep working. Imported archives are normalised on load. No record is lost.

Tasks **without a due time are never given an invented notification time**: the editor blocks
the save with an explanation, and Settings › Reminder Engine lists any such entries under
ENGINE DIAGNOSTICS.

### Recurrence, snooze, missed

- Daily / weekly / monthly events expand to real occurrences; each occurrence has its own
  reminder identity, so later occurrences always fire and never duplicate. Monthly series
  are anchor-based — see *Monthly recurrence* below.
- Recurring **tasks** keep the existing behaviour (next cycle materialises on completion).
- Changing an entry's date, time, repeat rule or offsets changes the reminder identity →
  the old schedule is retired and the new one is armed.
- **Snooze** 5 / 10 / 15 / 30 min: persisted in the ledger, survives restarts, repeatable,
  and cancelled automatically when the task is completed or the entry deleted.
- **Missed detection** looks back 24h on launch and on resume; completed/deleted entries are
  ignored, nothing is delivered twice, and more than three misses collapse into one summary.

### Monthly recurrence (Stage 03.1 correction)

Monthly occurrences are **anchor-based**. Earlier builds advanced a cursor with
`Date.setMonth()`, which overflows — `2026-01-31 + 1 month` became **2026-03-03**, skipping
February *and* permanently corrupting every later occurrence (Apr 3, May 3 …).

The corrected rules:

| Rule | Behaviour |
| ---- | --------- |
| Anchor | The original day-of-month is the series anchor. |
| Short months | Clamp to that month's final valid day (Jan 31 → Feb 28). |
| Restoration | The anchor returns as soon as a month is long enough (Feb 28 → **Mar 31**). |
| Leap years | Follow the real length of February (2024-01-31 → **Feb 29**). |
| Drift | Zero — each occurrence is derived from the series start **plus an index**, never from the previous (possibly clamped) occurrence. |

```
2026-01-31 →  01-31  02-28  03-31  04-30  05-31
2024-01-31 →  01-31  02-29  03-31  04-30        (leap)
2026-08-31 →  08-31  09-30  10-31  11-30  12-31
2026-05-30 →  05-30  06-30  07-30  08-30
```

**One implementation, shared.** All recurrence maths lives in **`electron/recurrence.ts`**
(pure, zero imports). It is imported by *both* `electron/reminder-core.ts` (background
scheduler) and `src/lib/time.ts` → `src/lib/schedule.ts` (calendar, events page, dashboard).
There is deliberately no second copy, so the UI and the notification engine cannot drift
apart — and an automated parity test bundles the **real renderer code** and diffs its
occurrence dates against the **real scheduler** to prove it.

**Recurring tasks** keep their anchor across cycles: completing a Jan 31 monthly task
spawns Feb 28, and completing *that* spawns Mar 31 (not Mar 28). The anchor travels with
the spawned task.

**Backward compatibility.** The anchor is stored in a new **optional** field
`repeatAnchorDay`. Records written before Stage 03.1 simply derive it from their `date`, so
nothing breaks and no data is rewritten destructively. A `v3 → v4` store migration stamps
the field for existing monthly entries (purely additive; non-monthly entries untouched),
and imported JSON archives are normalised the same way.

### Reminder identity & states

`kind : entryId : occurrenceDate T occurrenceTime : +offset` — e.g.
`event:e1:2026-11-10T14:00:+60`. States: `delivered · snoozed · missed · cancelled`.
A corrupt or missing ledger degrades to empty (invalid rows dropped, valid rows kept) and
**never** touches the task/event database.

### Notifications & sound

Windows toasts are built with `toastXml` + `activationType="protocol"`, giving real action
buttons — **Mark complete · Snooze 10 min · Open** (events omit complete). Activation routes
through the registered `waypoint://` protocol, so buttons work whether the app is running or
is launched by the click. `AppUserModelId` is set to `com.waypoint.console` and the NSIS
installer creates the required Start Menu shortcut.

Actions that write data are dispatched to the **renderer** over IPC (it is the single
authoritative DB writer); snooze is handled in main, against the ledger only.

**Sound:** SUBTLE (default) · SYSTEM · SILENT.

> **Documented limitation:** Windows toast XML can only reference built-in
> `ms-winsoundevent` sounds — custom audio files are an MSIX-only feature and Electron's
> custom `sound` option is macOS-only. SUBTLE therefore mutes the toast and plays the
> bundled `assets/notify-subtle.wav` through a hidden renderer. If that fails for any
> reason the notification is still delivered silently; choose SYSTEM for the guaranteed
> native Windows chime. Sound failures can never block a notification.

### Notification history

Settings › Reminder Engine › **HISTORY** opens a slide-over listing delivered, snoozed and
missed reminders with timestamps, entry, offset and state, filterable by state. Clearing it
removes delivery records only — tasks, events and pending snoozes are preserved. No new
navigation was added.

`asarUnpack: assets/**` so the tray icon and `notify-subtle.wav` stay on the real
filesystem (both are read from disk at runtime). The app/installer icon is generated to
`build/icon.png`.

The NSIS target creates Desktop **and** Start Menu shortcuts. The Start Menu shortcut is
**required** for Windows toast notifications to display and must match the
`AppUserModelId` (`com.waypoint.console`) the app sets at startup — so always verify toasts
with the **installed** build rather than `electron .`.

**Packaging result in this sandbox:** electron-builder completed the application package —
`release/win-unpacked/WAYPOINT.exe` was produced with `dist/` + `dist-electron/` inside
`app.asar` and `assets/` in `app.asar.unpacked/`. The final installer step then failed with
`spawn wine ENOENT`, because compiling an NSIS installer from Linux requires wine. **On
Windows this step runs natively** and emits `release/WAYPOINT-Setup-<version>.exe`.

### Local operator authentication

The desktop console asks for a single operator on first launch. The access key
must be 12–128 characters; spaces are allowed. Subsequent launches require the
same credentials. The verifier is stored separately in the Electron user-data
directory (`waypoint-auth.json`), using a random salt and scrypt; the access key
is never saved. Keep a safe record of the credentials: there is no in-app
recovery or account management. The Daily Briefing remains accessible without
authentication, including its displayed data, and the browser-only preview
does not provide the desktop authentication service.

This is a local application access gate, not encryption of the existing data
store or a defense against someone with access to the OS account and files.
Hiding the console to the tray does not end the current authenticated session;
a full application quit ends it.


#### Session and security architecture

The Electron main process is the authentication authority, not React state.
After setup or verification it binds an in-memory session to the main window's
actual WebContents. Sensitive IPC requires that WebContents, its main frame,
the trusted console URL, and an active session. Navigation/reload, renderer
termination, window destruction, and process exit invalidate it. Closing to
tray retains the session. Tray directives wait until the authenticated console
is ready. Console persistence is not hydrated before authentication.

The Daily Briefing opens automatically on normal app launches and Windows
startup when the existing `briefingAtLogin` preference is enabled. Disabling
that preference suppresses automatic opening; the Settings preview remains
available.

The login screen can request only the local appearance preference and the auth
operations. The separate Daily Briefing window can request a read-only,
minimized snapshot needed for its display, open the console, or dismiss itself;
it cannot call the privileged storage or reminder APIs. The snapshot is
refreshed periodically and intentionally reveals the briefing's contents
without login. Background reminders and OS notifications continue independently
of the console session; notification content may therefore also be visible on
the machine. Notification actions originating outside the renderer retain their
existing OS integration, and console-bound actions are queued until login.

New verifiers use asynchronous scrypt (N=131072, r=8, p=1, 64-byte output,
256 MiB maxmem) and a random salt. Existing Stage 04A verifiers upgrade after a
successful login. A local, persistent, bounded progressive delay slows repeated
failures, and resets after success; it is not a permanent lockout. Neither the
verifier nor this throttle protects against a person who can modify local files,
use another process with the same OS account, or read the unencrypted operations
store. Use Windows account security and disk encryption for that threat model.
The web preview is not an authentication security boundary.

Run `npm test` for the credential, throttle, briefing snapshot, mocked Electron
IPC/session integration, reminder, and recurrence tests. The IPC suite executes
real handlers against mocked Electron objects; it does **not** replace testing
in a real Electron runtime or on Windows. Windows startup, tray, notifications,
